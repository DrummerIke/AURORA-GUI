# AURORA: roadmap источников и сводной аналитики

Дата проверки: 25 июля 2026 года.

## Какой отчёт нужен

AURORA должна показывать не выдачу поисковика, а карточку субъекта:

1. краткий вывод и уровень подтверждения личности;
2. подтверждённое ФИО и заявленное ФИО;
3. компании и профессиональные связи;
4. контактные идентификаторы;
5. публичные профили;
6. важные несоответствия и ограничения покрытия;
7. доказательства только для каждого принятого claim;
8. технические статусы и отброшенный мусор в закрытых блоках.

Этот формат реализован в `aurora/report_renderer.py`. Отсутствующие данные отображаются как «не подтверждено», а не заменяются списком похожих страниц.

## Какие классы решений изучались

- **Graph OSINT:** Maltego и SpiderFoot полезны как источники связей и orchestration, но их находка всё равно должна пройти AURORA EntityResolver.
- **Investigative knowledge graphs:** OCCRP Aleph предоставляет документные и entity-oriented интерфейсы. Документация разработчика была доступна из среды аудита: `https://docs.aleph.occrp.org/developers/`.
- **Sanctions/PEP screening:** OpenSanctions подходит для отдельной проверки уже известного лица или организации, но не для определения человека по телефону. Доступ к документации из среды аудита вернул HTTP 503, поэтому адаптер не объявляется подключённым.
- **Corporate registries:** OpenCorporates и официальные государственные реестры следует подключать по названию/регистрационному номеру организации после проверки лицензии, тарифа и регионального покрытия.
- **Username discovery:** Sherlock и Maigret полезны только после появления проверенного username.
- **Email registration signals:** Holehe полезен только для уже известного email и не доказывает владельца аккаунта.
- **Phone metadata:** PhoneInfoga, `phonenumbers`, Twilio Lookup, IPQS и Abstract дают формат, оператора, line type или репутацию, но не гарантированное ФИО.

## Что сознательно не подключается

AURORA не интегрирует «Глаз Бога», нелегальные базы утечек, Telegram-ботов обратного поиска, купленные дампы, обход авторизации и скрытые API. Такие источники не дают воспроизводимой цепочки доказательств, создают правовые и информационные риски и неприемлемы для кадрового решения.

Система предназначена для проверки данных, предоставленных кандидатом с законным основанием. Она не должна автоматически деанонимизировать частное лицо или принимать решение о найме.

## Приоритет следующей реализации

1. Search Provider interface с официальным API и сохранением provider result ID.
2. Безопасный ContentFetcher с SSRF-защитой, DNS pinning, лимитом размера, MIME allowlist и retention.
3. OrganizationResolver: название, ИНН/ОГРН, официальный сайт и роль человека — только по документному контексту.
4. Адаптер Aleph для уже известного ФИО/организации и разрешённого purpose.
5. Адаптер OpenSanctions для отдельного compliance-этапа; совпадение по одному имени должно оставаться гипотезой.
6. Entity graph с типизированными отношениями и evidence на каждом ребре.
7. PostgreSQL/Redis worker, повтор неуспешных источников, authentication и immutable audit log перед многопользовательским deployment.

Ни один будущий адаптер не считается подключённым, пока нет контрактных тестов ответа, обработки 401/429/timeout и документированной лицензии/ToS.
