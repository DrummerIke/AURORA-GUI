# Аудит текущего состояния AURORA

Дата аудита: 25 июля 2026 года.

## Резюме

Приложение запускается как локальный Flask/Waitress-сервис, сохраняет кейсы в файловой системе и имеет отдельные режимы телефона, email и username. Последний патч добавил общий `pipeline.py`, но описание предыдущего PR заметно опережало реализацию: retries, backoff, cache, постоянный circuit breaker, очередь, PostgreSQL и Redis фактически не были включены в рабочий путь. Часть API-адаптеров возвращала сырой фрагмент JSON вместо нормализованных сущностей.

Главная функциональная ошибка телефонного режима: `EntityResolver` находил кандидатов ФИО, но только помещал отклонённые значения в журнал и **никогда не создавал Entity типа `person`**. Поэтому корректное ФИО не могло появиться в отчёте при любых результатах поиска.

## Что реально работает

- локальный web-интерфейс на `127.0.0.1:8080`;
- файловая история в `cases/`;
- E.164-нормализация, страна, регион и возможный оператор через `phonenumbers`;
- DDGS-поиск точных публичных упоминаний;
- изоляция ошибки и timeout одного коннектора;
- честный `CONFIGURATION_REQUIRED` при отсутствии ключа или CLI;
- CLI Sherlock, Maigret, Holehe и PhoneInfoga запускаются только если действительно установлены;
- RDAP, crt.sh, Wayback, GitHub и DNS выбираются для соответствующих типов, но не для номера телефона.

## Почему поиск был слабым

1. По телефону выполнялся только один запрос в E.164. Российские страницы часто публикуют номер через `8`, без кода страны или с другим форматированием.
2. ФИО не переходило из кандидата в сущность даже при двух независимых подтверждениях.
3. Поисковые snippets использовались как evidence с низкой надёжностью; содержимое первоисточника не загружалось и не проверялось.
4. Нет полноценного Search Provider API: DDGS может менять поведение, ограничивать частоту или не индексировать нужный российский источник.
5. PhoneInfoga даёт метаданные и поисковые ссылки, но не является надёжной базой владельцев номера и не гарантирует ФИО.
6. Sherlock/Maigret работают по уже известному username, Holehe — по уже известному email; они не превращают телефон в личность.
7. В кодовой базе остаётся старый параллельный контур (`web_search_engine.py`, `identity_service.py`) с другой моделью confidence и фиолетовыми стилями. Телефонный worker его больше не использует, однако это технический долг.

## Исправлено в этом обновлении

- Добавлен поиск российских вариантов номера: E.164, `8XXXXXXXXXX`, десять цифр, плюс совместный запрос с заявленным ФИО.
- Реализовано принятие русского ФИО только при контексте номера и двух независимых, не клонированных источниках либо одном структурированном доверенном evidence.
- Клоны с одинаковым `content_hash` считаются одним подтверждением.
- Расширен RU/EN stoplist шаблонов, форм, CTA и телефонных каталогов.
- Добавлен безопасный сценарий проверки: работодатель вводит ФИО, предоставленное кандидатом, цель и подтверждает законное основание. Это проверка заявленной связи, а не автоматическая деанонимизация.
- Purpose и consent сохраняются в метаданных кейса.
- Итоговый HTML переработан из списка сайтов в executive report: сначала выводы о личности и компании, затем контакты/профили и только после них evidence. Технические статусы закрыты по умолчанию.
- Добавлено консервативное извлечение российских юридических названий с обязательным контекстом телефона и независимым подтверждением.

## Реальные источники и ограничения

### Без ключа

- `phonenumbers`: метаданные плана нумерации, не владелец;
- DDGS: поисковый индекс, snippets требуют ручной проверки;
- PhoneInfoga CLI: только при установленном бинарнике;
- RDAP, crt.sh, Wayback, GitHub, DNS: применимы к доменам/IP/email/username, а не к обратному поиску владельца телефона;
- Sherlock/Maigret/Holehe: применимы после получения соответствующего идентификатора.

### С ключами

`VIRUSTOTAL_API_KEY`, `SHODAN_API_KEY`, `CENSYS_API_ID`, `CENSYS_API_SECRET`, `SECURITYTRAILS_API_KEY`, `HIBP_API_KEY`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `IPQUALITYSCORE_API_KEY`, `ABSTRACT_PHONE_API_KEY`, опционально `GITHUB_TOKEN`.

Эти API не следует рекламировать как источники ФИО. Twilio/IPQS/Abstract могут дать line type, carrier и репутационные сигналы согласно тарифу и региональному покрытию.

## Проверка внешних GitHub-проектов

В среде аудита запросы к GitHub API и web-search были заблокированы proxy (`403 Forbidden` / `401 Unauthorized`), поэтому актуальные релизы и лицензии нельзя было честно перепроверить онлайн. Скрипт установки использует официальные package names и не закрепляет непроверенные fork/release. Перед production-обновлением запустите `python scripts/doctor.py` и проверьте ссылки в `docs/CONNECTORS.md` из сети владельца.

## Что необходимо следующим этапом

1. Добавить официальный Search Provider (Bing Web Search, Google Programmable Search или Yandex XML/API при договоре и разрешённом сценарии), сохраняющий URL и snippet.
2. Реализовать безопасную загрузку первоисточника: DNS pinning, запрет private IP, ограничение размера, MIME и redirect, HTML sanitation, TTL.
3. Нормализовать ответы каждого платного API в claims вместо сохранения фрагмента JSON.
4. Перевести email/username на тот же pipeline и удалить старую дублирующую модель только после миграционных тестов.
5. Для многопользовательского сервера добавить authentication, authorization, audit log, шифрование и реальное retention deletion. GitHub Pages для backend не подходит.
6. Решения о найме нельзя принимать автоматически по score AURORA: результат должен проверять уполномоченный сотрудник по первоисточникам и применимому законодательству.
7. План законных graph/compliance/corporate интеграций находится в `docs/OSINT_ROADMAP.md`; непрозрачные агрегаторы и базы утечек исключены.
